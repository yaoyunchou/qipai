### 已关闭：直播插件（2026-10-07 15:20）

**背景**：`live-player-plugin`（provider `wx2b03c6e691cd7370`）是本项目唯一的第三方插件依赖，
移除后可减少审核关注面与包体积。

**依赖链梳理**（改动前查清，避免漏改）：
```
app.json → pages/live 分包（含 plugins 声明）
              ↓
pages/live/index.json → plugin-private://wx2b03c6e691cd7370/components/subscribe/subscribe
              ↓
app-diy-page.json → "app-live": "/components/page-component/app-live/app-live"
              ↓
app-diy-page.wxml → <block wx:if="{{id==='live'}}"><app-live .../></block>
              ↓
app-diy-page.js  → ① F=function(){t.e(".../app-live").then(...)}  ② components 映射 appLive:F
app-live.js      → 点击时 navigateTo("plugin-private://.../live-player-plugin?room_id=")
pages/index/index.js → 处理后端下发的 live 跳转路径（plugin-private:// 前缀判断）
```

**实际改动（5 处 + 删 2 目录）**：
| 文件 | 改动 |
|---|---|
| app.json | 删除 `pages/live` 整个分包对象（含 plugins 声明）。分包数 62 → 61 |
| app-diy-page.json | 删除 `"app-live"` 组件声明 |
| app-diy-page.wxml | 删除 `<app-live>` 标签，**保留空的 `<block wx:if="{{id==='live'}}"></block>`** 以维持 if/else 链不错位（-137 字符）|
| app-diy-page.js | 删除 `F=function(){t.e("...app-live")...}` 异步加载映射（-134 字符）|
| app-diy-page.js | 删除组件注册表 `appLive:F`（**必须同步删，否则 ReferenceError 崩溃**）|
| 文件删除 | `pages/live/`（4 件套）、`components/page-component/app-live/`（4 件套）|

### 🔴 阻塞项：jd.jxfg.top 被腾讯云 DNSPod 封禁（2026-10-07 16:05 修正）

**重要修正**：15:47 判定为「nginx 证书未生效」，**该判断错误**。
用户反馈"浏览器能打开"后重新排查，找到真因。

**决定性证据**：
```
curl http://jd.jxfg.top/web/index.php?_mall_id=1&r=api/index/config
→ HTTP/1.1 302 OK
→ Location: https://dnspod.qcloud.com/static/webblock.html?d=jd.jxfg.top
```
**全路径均被拦截**（`/`、`/anything/test` 等任意路径均 302 到同一 webblock 页）
→ 腾讯云 DNSPod 的**域名封堵页**，说明该域名在腾讯云侧被违规封禁。

**为何表象是 TLS 握手失败**（关键坑点）：
80 端口有响应（302），但 **443 端口一个字节都不返回，直接 RST**：
```
schannel: failed to receive handshake, SSL/TLS connection failed
[WinError 10054] 远程主机强迫关闭了一个现有的连接
Python: RemoteDisconnected: Remote end closed connection without response
```
域名被封后 443 服务实际不存在，故表现为"证书错误"。**属误判陷阱。**

**浏览器为何"能打开"**：
浏览器自动跟随 302 跳到 `dnspod.qcloud.com/static/webblock.html`，
用户看到的是一个**能正常渲染的拦截提示页**，误以为站点可访问。
但小程序需要 JSON，拿到的自然是 HTML → `r.code` 为 undefined → reject undefined → 首页白屏。
⚠️ **典型「浏览器能开 ≠ 接口可用」陷阱。**

**排查矩阵（可复用）**：
| 测试路径 | 结果 |
|---|---|
| curl 走系统代理 | HTTP 000 |
| curl `--noproxy "*"` 直连 443 | exit 35 握手失败 |
| curl `--tlsv1.2 --tls-max 1.2` | 仍失败（排除协议协商）|
| curl `--http1.1` | 仍失败 |
| Python urllib 忽略证书校验 | RemoteDisconnected |
| **curl 80 端口** | **302 → dnspod webblock（决定性）** |

📌 **教训**：遇 TLS 握手失败必须**同时测 80 端口**。
两者行为不一致（80 有响应 / 443 完全无响应）才能定位到封堵/防火墙层，
而不是证书层。

**需处理（域名层面，前端无法绕过）**：
- 若因未备案：需在腾讯云完成备案后绑定国内主机
- 若因违规封禁：需向腾讯云申诉解封
- 换域名只是暂缓，同主体/备案问题会复发

**⚠️ 业务合规提醒**：项目名 `zjhj_bd_app`（棋牌）。国内主体经营棋牌类业务
涉及**版号与合规红线**，域名封禁与小程序审核均可能受阻，建议尽早核实资质。

### 排查方法论沉淀（可复用）
排查「浏览器能开但工具失败」的正确顺序：
1. **先分离网络层与应用层** —— 用裸 socket / curl exit code 判断

### 「一条成功一条失败」的真相：两条都失败（2026-10-07 16:14）

用户提供两条 `api/cat/list` 的 curl，称一条成功一条失败。**逐条原样执行后：两条都失败。**

| 命令 | 用户认知 | 实测退出码 | 结论 |
|---|---|---|---|
| A（Referer: 127.0.0.1:18371/） | 成功 | **56**（首次）/ 35（复测）| ❌ 失败 |
| B（authority + sec-fetch-*） | 失败 | **35** | ❌ 失败 |

**排除的变量（逐项测试，均无影响）**：
| 假设 | 实测 | 结论 |
|---|---|---|
| 请求头差异 | 换微信 UA / Chrome UA / authority 头 | 全 35，**无关** |
| 是否走代理 | 代理 3 次 vs 直连 | 全失败，**无关** |
| 接口路径差异 | cat/list、cart/list、config | 全失败，**无关** |
| 是否间歇性 | 同请求连测 10 次 | 全 35，**但首跑出现过 56** |

**curl 退出码语义（本次关键）**：
- `35` = SSL connect error —— TLS 握手阶段失败，ClientHello 后即被 RST
- `56` = Recv failure: Connection reset by peer —— **TCP 已建、请求已发出**，
  但等响应时被 RST

命令 A 首次出现 56，说明那次**握手侥幸通过、请求真的发出去了**，响应阶段仍被重置。
→ **服务端防护是「间歇性放行」**，这解释了用户为何觉得"有时能通"。
用户看到的"成功"很可能是 Network 面板里那条记录没报红，或复制 curl 时误以为拿到了响应。

📌 **方法论**：「同一接口一条成功一条失败」先怀疑观测手段，别急着找业务差异。
1. 把用户声称成功的命令**原样跑一遍**（本例直接推翻前提）
2. **记录退出码而非只看 HTTP 码** —— HTTP 000 时退出码才区分故障层级
3. **连测 ≥5 次** —— 区分稳定失败与间歇失败
4. 最后才考虑业务/代码差异

⚠️ 本次若直接去分析两条命令的 `sec-fetch-*` / `authority` 头差异，
会陷入无意义的比较，永远找不到答案——**因为它们都失败**。
