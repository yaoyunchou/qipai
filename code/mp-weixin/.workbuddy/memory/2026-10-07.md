用户要求关掉直播。这是项目里**唯一的第三方插件依赖**。

**依赖链（5层，关之前必须查清，漏一层就白改）**：

**改动**：app.json 删分包 / app-diy-page.json 删声明 /

### 🔥 关键教训：webpack 产物改变量必须「声明+引用」成对处理
`F=function(){t.e("...app-live")...}` 是**声明**，`appLive:F` 是**引用**。
只删声明 → 运行时 `ReferenceError: F is not defined` → 组件白屏崩溃，
而且 **JS 语法校验完全查不出来**（语法合法，只是运行期报错）。
必须 `grep -E '[,:{]\s*F\s*[,}\]]'` 扫一遍引用点才能发现。
以后改任何 webpack/miniprogram_npm 产物里的变量，固定三步：
删声明 → 搜引用 → 删引用 → 跑 node --check。

### 另一个坑
wxml 里删组件标签时，若原本在 `wx:if/wx:else` 链中间，
**要留空 `<block wx:if="..."></block>` 壳**，否则整个 else 链会错位挂到错误分支上。

**结果**：分包 62→61，594 个 JS 零语法错误，插件引用全清，
主包 1.963MB → 1.937MB（省 27KB，余量从 34.7KB 涨到 64.4KB）。

**遗留**：pages/index/index.js 里的 live 路径判断逻辑没动。
若微擎后台上架配置还下发 live 模块，前端会拼出`/plugin-private://...`
这种无效路径跳转失败。**需在微擎后台关闭直播模块才算真正闭环**（已写入档案待办）。

**备份**：`.workbuddy/backup/2026-10-07-关闭直播/`（4个文件.bak + 已移除文件/live + app-live）

### 校验脚本自身踩的坑

## 追加：运行时错误定位（15:40）—根因是后端域名失效

用户报编译已过，但控制台报：
```
Uncaught (in promise) undefined(env: Windows,mp,2.02.2607161; lib: 3.17.2)
The resource .../WAServiceMainContext.js was preloaded...  ← 无害的浏览器提示，可忽略
```

### 排查链条
1. 报错上下文 `contextName=app` → 定位到 App onLaunch 阶段
2. onLaunch 里三个调用：`wx.getSystemInfo`（有 success 回调）、
   `$store.dispatch("mallConfig/actionGetConfig")`、`$user.silentLogin()`
3. 查 vendor.js：`silentLogin:function(){}` 是**空函数**，无辜；
   `actionGetConfig` 带 `.catch(function(){})`，也无辜
4. 深挖 `$mallConfig.getConfig()`，找到**真正的病灶**：

```js
f = function(e, t) {          // e=resolve, t=reject
  e && p.push(e); t && d.push(t); c || (c = true,
    request({url: api.index.config}).then(function(r){
      if (0 === r.code) { ... p[t](l); p = []; }
      else { for (var n in d) d[n](r.msg); d = []; }   // ← reject(r.msg)
    }).catch(function(e) {
      for (var t in c = false, d) d[t](e.msg); d = []; // ← reject(e.msg)
    }))
}
```
**`reject` 传的实参是 `e.msg`**。请求失败时 wx 给的error 对象**没有 `msg` 字段**
（只有 `errMsg`），于是 `reject(undefined)` → 控制台 `Uncaught (in promise) undefined`。

### 但真正的根因在后端：hjsc.com 已经是域名停放页
实测 `curl http://hjsc.com/web/index.php?_mall_id=1/api/index/config`：
```
HTTP 200，但返回 <title>hjsc.com - 该网站正在出售！ - Hjsc 资源和信息。</title>
```
sedoparking 的域名出售停放页 + JS 跳转，**不是微擎后端的 JSON**。
DNS 解析到 64.190.63.222（停放服务 IP）。
→ 接口拿到 HTML，`r.code` 为 undefined ≠ 0 → 走 else → `d[n](r.msg)` → `r.msg` 也是 undefined。

### 结论
`Uncaught (in promise) undefined` **不是代码 bug，是环境问题**：
项目拷来时 `siteinfo.js` 指向的 `hjsc.com` 已经不是原微擎后端了。
前端拿不到 `mallConfig`（商城全局配置：导航、主题、是否显示购物车…），
所以首页必然渲染异常/空白。**改代码治不好，必须换 apiroot 指向真实后端。**

### 顺带结论
- 上一轮关直播省下的27KB 有意义，但**包体积从来不是这次的阻塞点**
- `Uncaught (in promise) undefined` 的通用定位法：
  搜 vendor/产物里 `reject` 调用，检查实参是否用了 `.msg`（应为 `errMsg`）。
  这是微擎/we7 系小程序的**通用坑**（宿主 wx error 对象是 errMsg）。

### 可选修复（需用户决定，我没动）
- 若只是想让App 启动不报错：给 `getConfig` 的两个 reject 补fallback 实参（如 `e.errMsg||"config 请求失败"`），
  但首页仍会因缺 mallConfig 而空白——**治标不治本**。
- 正解：把 `siteinfo.js` 的 `apiroot` 换成真实后端地址。

## 追加修正：不是证书问题，是腾讯云 DNS 拦截（16:02）

用户反馈"我用浏览器能打开"，推翻了我上一轮「证书没配」的判断。重新排查后找到真因。

### 🔥 决定性证据
```
curl http://jd.jxfg.top/web/index.php?_mall_id=1&r=api/index/config
→ HTTP/1.1 302 OK
→ Location: https://dnspod.qcloud.com/static/webblock.html?d=jd.jxfg.top
```
**全路径拦截**（根路径、`/anything/test` 任意路径 302 到同一个 webblock 页）。
这是**腾讯云 DNSPod 的域名封堵页**，说明该域名在腾讯云侧被**违规封禁**（备案违规/未备案/涉赌等）。

### 为什么表现成 TLS 握手失败（关键坑点）
80 端口有响应（302），但**443 端口一个字节都不返回**，直接 RST：
```
schannel: failed to receive handshake, SSL/TLS connection failed
[WinError 10054] 远程主机强迫关闭了一个现有的连接
```
`RemoteDisconnected: Remote end closed connection without response`（Python，忽略证书也一樣）
→ 所以表象是"证书问题"，实际是**域名被封后 443 服务根本不存在**。
我上一轮误判为"nginx 监听 443 但证书无效"，教训：**遇到 TLS 握手失败，
必须同时测 80 端口看是否有响应**，两者行为不一致才能定位到封堵/防火墙层。

### 浏览器为什么"能打开"
浏览器会**自动跟随 302 跳转**到 `dnspod.qcloud.com/static/webblock.html`，
用户看到的是一个**能正常显示的拦截提示页**，误以为"网站能访问"。
但小程序要的是 JSON，拿到的自然是 HTML → `r.code` undefined → reject undefined → 白屏。
**这是典型的「浏览器能开 ≠ 接口可用」陷阱。**

### 已做的排查矩阵（供复用）
| 路径 | 结果 |
|---|---|
| curl 走系统代理 127.0.0.1:62780 | HTTP 000 |
| curl --noproxy "*" 直连 443 | exit 35 握手失败 |
| curl --tlsv1.2 --tls-max 1.2 | 仍失败（排除协议协商）|
| curl --http1.1 | 仍失败 |
| Python urllib 忽略证书校验 | RemoteDisconnected |
| curl **80 端口** | **302 → dnspod webblock** ← 决定性 |

### 结论与后续
域名 `jd.jxfg.top` 当前**不可用于小程序**，需先解决封禁：
- 若是未备案：腾讯云要求备案后才能绑定国内主机
- 若是涉赌/违规：需申诉解封（`棋牌`类业务在此域名上，很可能是这个原因）
- 换域名也只是暂缓，同样主体/备案问题会复发

⚠️ **注意业务风险**：项目名 `zjhj_bd_app`（棋牌），国内主体做棋牌类业务本身
涉及**版号与合规红线**，小程序审核也会卡。后续要留意。

## 追加：开发者工具 ERR_CONNECTION_RESET 完全印证（16:06）

用户贴出开发者工具 Network 面板截图/日志，关键错误：
```
GET https://jd.jxfg.top/web/index.php?_mall_id=1&r=api/cart/list
net::ERR_CONNECTION_RESET
```

### 这个错误码就是终极证据
`ERR_CONNECTION_RESET` = TCP 连接被 RST 重置，与我用 Python 裸 socket 测到的
`ConnectionResetError [WinError 10054]` **完全对应**：
```
TCP 443 已连接 → 发送 ClientHello → TLS 中断：ConnectionResetError
```
即：**TCP 三次握手成功，但服务端在收到 ClientHello 后立即 RST**。
这不是应用层问题（不是 4xx/5xx，不是 JSON 格式错，不是 CORS），
是**连接在 TLS 握手阶段就被掐断** → 请求根本没进到 nginx/PHP。

复测 cart/list 同样 `curl exit=35`（35 = SSL connect error）。

### 封禁范围扩大确认
不只是 jd 子域，**整个 jxfg.top 主域下都被封**：
| 主机名 | 结果 |
|---|---|
| jd.jxfg.top | 302 → dnspod webblock |
| www.jxfg.top | 302 → dnspod webblock（同样被封）|
| jxfg.top（裸域）| 无响应 |
| api.jxfg.top / admin.jxfg.top | 无响应（未解析/无记录）|

→ 换子域没用，必须解封或换主域。

### 💡 方法论沉淀（本次排查最值钱的收获）
排查「浏览器能开但工具失败」这类问题的正确顺序：
1. **先分离网络层与应用层**：用裸 socket / curl exit code 判断是连接问题还是响应问题
   - `curl exit 35` / `WinError 10054` / `ERR_CONNECTION_RESET` → 网络层，后端根本没收到请求
   - `HTTP 4xx/5xx` → 应用层，去看 JSON 和业务错误码
2. **再对比 80 与 443**：80 有响应 + 443 完全无响应 → 封堵/防火墙/证书层
3. **最后才看请求头/前端代码**：请求头、CORS、referrer 都排到最后
   （本例中请求头完全正常，`x-app-platform: wxapp` 等无任何问题）

⚠️ 反复出现的坑：**不要因为看到「TLS 握手失败」就断定是证书问题**。
必须同时测 80 端口。本次若只测 443，会一直往证书方向找原因，完全找错方向。

## 追加：「一条成功一条失败」的真相 — 两条都失败（16:14）

用户贴了两条 curl（同一接口 `api/cat/list`），说一条成功一条失败，问为何不同。
逐条原样执行后结论：**两条都失败，成功是误判**。

### 实测结果
| 命令 | 用户认知 | 实际退出码 | 结论 |
|---|---|---|---|
| 命令 A（Referer: 127.0.0.1:18371/） | 成功 | **56**（首次）/ 35（复测） | 失败 |
| 命令 B（authority + sec-fetch-*） | 失败 | **35** | 失败 |

裸请求（无任何自定义头）连测 5 次：全35。
带完整微信 UA 连测10 次：**全是 35**，无一成功。
命令 A 形式连测 10 次：全 35。
走系统代理 3 次 / 直连 1 次：全 35。

**→ 不存在「成功」的情况，两条命令等价。**

### 关键新发现：curl 退出码 56 vs 35 的区别
- **35 = SSL connect error**：TLS 握手阶段失败（ClientHello 后被RST）
- **56 = Recv failure: Connection reset by peer**：TCP 已建、**请求已发出**，
  但在等响应时被 RST

命令 A 首次出现 56，说明那一次**握手侥幸通过、请求真的发出去了**，
但响应阶段仍被重置。所以用户看到"成功"很可能是：
- 开发者工具 Network 面板里那条记录**没有报红**，或
- 复制 curl 时误以为拿到了 JSON，实际响应体是空的

⚠️ **56 出现说明服务端 TLS/防护是「间歇性放行」的**，
不是完全拒绝。这解释了用户为何会觉得"有时能通"。

### 排除的变量（逐个测试均无影响）
| 假设 | 实测 | 结论 |
|---|---|---|
| 请求头差异导致 | 换微信 UA / Chrome UA / authority 头 | 仍全 35，**无关** |
| 是否走代理 | 代理 3 次 vs 直连 1 次 | 都失败，**无关** |
| 是否间歇性 | 同请求连测 10 次 | 全 35，**但首跑出现过 56** |
| 接口路径差异 | cat/list、cart/list、config | 全失败，**无关** |

### 方法论沉淀（本次最大收获）
**「同一接口一条成功一条失败」先怀疑观测手段，别急着找业务差异。**
排查顺序：
1. **把用户声称成功的命令原样跑一遍** —— 本例直接推翻前提
2. **记录 curl 退出码而非只看 HTTP 码** —— HTTP 000 时退出码才区分得出
   35（握手失败）vs 56（响应被重置），这是不同故障层
3. **连测 ≥5 次** —— 区分稳定失败与间歇失败（本例正因此发现 56）
4. 再考虑业务/代码差异

⚠️ 本次若直接去找「两条命令的头有什么不同」，会陷入无意义的
`sec-fetch-*` / `authority` 差异分析，永远找不到答案——因为**它们都失败**。

## 追加：澄清「接口不稳定」（16:17）

用户问是否接口不稳定。**明确否定**，并给出判据。

### 对照组实验（证明本机网络正常）
| 目标 | 结果 |
|---|---|
| `api.github.com` | HTTP 200 正常 |
| `www.qq.com` | 有响应，能连通 |
| `jd.jxfg.top` | 退出码 35，不通 |
→ 本机网络、DNS、代理均无问题，**问题特定于该域名**。

### 「接口不稳定」与「域名不通」的本质区别
**接口不稳定**（后端代码/服务问题）：
- 请求**能到达服务端**，服务端内部出错
- 表现：HTTP 500 / 502 / 504，**时好时坏，偶发返回 200**
- 特征：Network 面板**能看到状态码**，能拿到响应体

**域名不通**（当前情况）：
- 连接层就断了，**请求从未进入应用层**
- 表现：`net::ERR_CONNECTION_RESET` / 退出码 35 / 56
- 特征：Network 面板**连状态码都没有**，响应体为空

### 请求旅程定位
```
DNS 解析     OK 成功（1.12.219.199）
TCP 三次握手  OK 成功
TLS 握手     被 RST <- 断在这里
HTTP 请求    从未发出
PHP 逻辑     从未执行
```
**接口代码再稳定，也轮不到它执行。**

### 判据口诀（下次直接套用）
- 看到**状态码**（哪怕是 5xx）→ 后端问题，查服务器日志 / PHP
- 看到 **`net::` 开头 / 无状态码** → 网络或域名问题，别碰后端代码

⚠️ 这条区分很重要：本次若误判为「接口不稳定」，会跑去查微擎后端日志、
PHP 代码、数据库，方向完全错误。实际上后端根本没被访问到，查什么都是空的。
